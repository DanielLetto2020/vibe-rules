# Граница между правилом и замком

Один вопрос решает, куда попадёт новое требование:

> **Может ли машина проверить это без участия человека и без модели?**

Если да — оно не должно жить в тексте. Текст модель прочитает и в большинстве
случаев выполнит; хук выполняется всегда, независимо от того, что модель решила
и что она успела запомнить среди сорока других инструкций.

## Значения `enforcement`

| Значение | Что означает | Где реализуется | Стоимость контекста |
|---|---|---|---|
| `hook` | блокируется до выполнения | `std-core/scripts/*.sh` | 0 |
| `lint` | падает в CI и локально | `configs/` модуля | 0 |
| `test` | ловится тестами | тесты проекта | 0 |
| `review` | требует человека, автоматизации не поддаётся | текст правила | по путям |
| `prose` | договорённость или причина решения | текст правила | по путям |

Первые три — замки: соблюдение не зависит от везения. Последние два — просьбы.

## Как выбрать

```
Требование
  │
  ├─ Опасное и необратимое действие (удаление данных, force-push)?
  │     → hook. Пиши скрипт в std-core/scripts/, добавь кейсы в tests/test-hooks.sh
  │
  ├─ Формализуемо как свойство кода (стиль, сложность, типы, зависимости)?
  │     → lint. Конфиг в configs/ модуля. Без конфига это не lint, а prose
  │
  ├─ Формализуемо как поведение системы?
  │     → test. Правило описывает, что именно должно проверяться
  │
  ├─ Цена ошибки не покрывается тестами (миграции, деньги, права, контракты)?
  │     → review. Правило обязано называть это явным списком
  │
  └─ Иначе → prose. Только причины и договорённости, которых нет в коде
```

## Что нельзя закрыть автоматикой в принципе

Этот список — граница подхода «не читать код». Здесь человек читает всегда,
независимо от того, насколько зелёные тесты:

- **миграции и изменения схемы БД** — откат кода занимает минуту, откат данных невозможен;
- **изменения существующего API-контракта** — тест проверяет вашу сторону, а ломается чужая;
- **новые зависимости** — вредоносный пакет проходит любые проверки идеально;
- **деньги, авторизация, персональные данные** — цена ошибки несоизмерима с ценой чтения;
- **конфиги CI/CD и прав доступа** — это и есть тот слой, который всё остальное охраняет;
- **производительность, гонки, стоимость эксплуатации** — тесты на happy path их не видят;
- **архитектурная энтропия** — код может быть корректным и при этом нерасширяемым.

## Почему доля неавтоматизированного должна падать

`tests/lint-modules.py` печатает при каждом прогоне, чем подкреплены правила:
сколько машиной (`lint`, `hook`, `test`) и сколько человеком (`review`,
`prose`). Метрика — вторая цифра, и считать в ней только `prose` было
самообманом: получалось 4% там, где неавтоматизировано две трети набора.

`review` — это «человек прочитает код», то есть ровно то, от чего репозиторий
обещает избавить. Часть этого чтения неустранима (список выше), но остальное —
задел на автоматизацию, а не достижение.

Правило перестаёт быть неавтоматизированным двумя способами: его автоматизируют
либо удаляют. Оба варианта — прогресс.

На 29 июля 2026: машиной 34 из 94, человеком 60 (`review` 56, `prose` 4).

## Проверка правила перед мерджем

1. Оно проверяемо? («до 15 строк в методе» — да; «пиши понятно» — нет)
2. У него есть владелец?
3. `enforcement` честный? (`lint` без конфига в `configs/` — самообман)
4. Оно не противоречит другому правилу? При конфликте модель выберет
   произвольное, и вы не узнаете какое.
5. Оно заведено по факту, а не впрок? Правило «на всякий случай» — это налог
   на каждую сессию каждого разработчика.
