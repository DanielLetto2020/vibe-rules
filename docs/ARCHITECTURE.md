# Архитектура: почему именно так

## Исходная задача

Claude Code начинает каждую сессию с чистого контекста. Всё, что команда хочет
сообщить, приходится сообщать заново — и здесь два неочевидных ограничения:

1. **У брифинга есть цена.** Постоянный контекст оплачивается токенами в каждой
   сессии каждого разработчика.
2. **Чем больше сказано, тем хуже соблюдается.** Документация прямо рекомендует
   держать CLAUDE.md под 200 строк: длинные файлы и расходуют контекст,
   и снижают следование инструкциям.

Значит вопрос не «что написать», а «куда положить, чтобы нашлось ровно тогда,
когда понадобится».

## Пять мест и что в них кладут

| Место | Механизм | Аналогия |
|---|---|---|
| Постоянный контекст | `CLAUDE.md` | утренний брифинг |
| По путям файлов | `.claude/rules/*.md` + `paths:` | табличка на станке |
| По задаче | `skills/*/SKILL.md` | инструкция на полке |
| По требованию | `docs/*.md` | библиотека в конце коридора |
| Не грузится вовсе | hooks, линтеры, CI | замок на станке |

Замок принципиально отличается от остальных четырёх: он не участвует в
контексте и работает независимо от того, что модель решила.

## Три решения, которые определили конструкцию

### 1. Правила остаются rules, а не превращаются в skills

Плагины Claude Code не раздают `.claude/rules/` — только skills, commands,
agents, hooks, MCP и LSP. Напрашивается упаковать конвенции стека скиллами:
тогда всё раздаётся штатно.

Мы этого не делаем. Скилл подбирается моделью по описанию — это вероятность.
Правило с `paths:` грузится по факту чтения файла — это детерминизм. Для
стандартов, которые обязаны действовать, вероятность не подходит.

Цена решения — симлинки. Она приемлема, потому что скрыта в скрипте.

### 2. Путь резолвится динамически

Плагины ставятся в `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`.
Путь **содержит версию**, поэтому симлинк на `${CLAUDE_PLUGIN_ROOT}` порвётся
при первом же `/plugin update`.

`std-link.sh` вместо этого читает `installLocation` маркетплейса из
`~/.claude/plugins/known_marketplaces.json` — это стабильный git-клон репозитория,
который обновляется, но не переезжает. Плюс `VIBE_RULES_HOME` как ручной
override для локальной разработки.

Симлинки абсолютны, поэтому уходят в `.gitignore`, а `SessionStart`-хук
проверяет их живость: молча сломанное правило хуже отсутствующего, потому что
все продолжают считать, что оно работает.

### 3. Тестируемость заложена в конструкцию, а не добавлена сбоку

Обычная судьба репозитория стандартов: текст написан, соблюдается ли — неизвестно.
Здесь каждый слой проверяется машиной:

- **Замки** — чистые функции: JSON на вход, `allow/deny/ask` на выход.
  Тестируются как обычный код, без модели и токенов.
- **Структура правил** — `lint-modules.py`: манифесты, frontmatter, мёртвые
  `paths:`, размер постоянного контекста, доля prose.
- **Фактическая загрузка** — хук `InstructionsLoaded` пишет журнал того, что
  реально попало в контекст. Это превращает вопрос «правило работает?» из
  предмета веры в проверяемый факт.

## Что эта система не решает

Честные границы важнее полноты:

- Тесты не ловят производительность, гонки, стоимость эксплуатации и UX.
- Корректный код может быть нерасширяемым: архитектурная энтропия метриками
  не измеряется.
- Если тесты пишет та же модель, что и код, — нужен независимый надзор
  (мутационное тестирование, разделение генерации кода и тестов, защита тестов
  от правки: этим занимается `guard-tests.sh`).
- Новая зависимость проходит любые проверки идеально.

Список того, что остаётся человеку, — в [ENFORCEMENT.md](ENFORCEMENT.md).
Он не сокращается по мере роста автоматизации, и это нормально.
