# Приведение старого кода к стандартам

Задача звучит как «переписать всё по правилам». Так делать нельзя: правка
на сотни файлов не читается человеком, не проверяется тестами, которых нет,
и разрушает историю обвинений в git — а взамен даёт код, который выглядит
современнее, но работает так же или хуже.

Правильная цель другая: **сделать так, чтобы долг не рос, а падал сам —
по мере обычной работы.** Механизм для этого уже есть, процедура его запускает.

> Массовая правка «под стандарт» — самый дорогой способ внести регрессию:
> она объёмна, скучна для ревью и не подтверждена ничем.

## 1. Измерь долг, прежде чем что-то менять

```
/std-gauntlet:run --only debt
```

Первый прогон фиксирует планку: столько несоответствий есть сейчас. Это
не приговор и не план работ — это точка отсчёта, ниже которой проект больше
не опустится.

Если считать нечем, скрипт скажет об этом прямо. Тогда задай команду подсчёта
в `.claude/gauntlet.json` → `debt.command`: подойдёт любой инструмент, который
печатает по строке на нарушение.

Покажи человеку число и объясни, что оно значит. Не предлагай «исправить всё».

## 2. Выбери участок по цене, а не по уродству

Кандидаты, в порядке ценности:

1. **Файлы, которые и так придётся тронуть** по текущей задаче — эти
   приводятся к правилам бесплатно, попутно.
2. **Файлы, которые меняются чаще всего** (`git log --format= --name-only |
   sort | uniq -c | sort -rn | head -20`) — вложение окупается быстрее всего.
3. **Файлы на пути новой функциональности** — их всё равно читать.

Не берись за код, который никто не трогал два года и не собирается: там долг
ничего не стоит, а риск регрессии реален.

## 3. Сначала сеть, потом ремонт

Непокрытый тестами код к стандарту не приводят. Сначала — характеризация:
процедура `legacy-characterize` фиксирует текущее поведение как эталон,
включая то, что выглядит багом.

Порядок нарушать нельзя: рефакторинг без эталона отличается от порчи кода
только намерением, а результат одинаковый.

## 4. Правь узко и однородно

- Один участок — один проход — один коммит. Правки «по правилам» не смешивай
  с изменением поведения: в ревью они неразличимы.
- Держи стиль соседних файлов, а не абстрактный идеал: единообразие внутри
  проекта важнее соответствия любому внешнему образцу.
- Правило, которое нарушено в проекте систематически, — кандидат не на правку
  кода, а на разговор с человеком: возможно, оно здесь неуместно, и честнее
  записать отступление (`/std-core:rule`), чем годами держать красный долг.

## 5. Убедись, что поведение не изменилось

```
/std-gauntlet:run
```

Характеризационные тесты обязаны остаться зелёными без правки. **Тест,
который пришлось поправить после рефакторинга, означает, что поведение
изменилось** — остановись и разберись, а не подгоняй эталон.

## 6. Зафиксируй новую планку

Успешный прогон опустит планку долга сам. С этого момента вернуться к прежнему
уровню нельзя: следующий, кто внесёт несоответствие, увидит красный гейт.

Если долг вырос по объективной причине — обновился линтер, ужесточился
конфиг — это решение человека, а не агента:

```
debt.sh reset <новое число>
```

## Чего делать не нужно

- Массовое переформатирование всего проекта одним коммитом.
- Приведение к стандарту файлов, которых не касается задача, «раз уж мы здесь».
- Правка чужого кода без теста под ним — даже если правка очевидна.
- Молчаливое снижение планки, чтобы гейт позеленел.
