# Новый модуль стандартов

Модуль — это плагин в `plugins/std-<slug>/`. Один модуль = один стек или
фреймворк. Дробить мельче не нужно: внутри модуля разделение идёт через `paths:`.

## Перед началом задай один вопрос

**Что из этого нельзя проверить машиной?** Если правило проверяется линтером,
типизатором или тестом — оно не должно попадать в текст. Текст — это просьба,
конфиг линтера — гарантия. Модуль, состоящий только из прозы, — плохой модуль.

## Шаги

### 1. Скопируй скелет

```bash
cp -r templates/module plugins/std-<slug>
```

### 2. Заполни `.claude-plugin/plugin.json`

Имя обязательно совпадает с именем директории. `version` ставь явно: без него
каждый коммит считается новой версией, и пользователи получают обновления
непредсказуемо.

### 3. Напиши правила в `rules/`

Один файл — одна тема. Обязательный frontmatter:

```yaml
---
paths: ["app/Http/**/*.php"]     # без этого правило грузится ВСЕГДА
owner: "@backend"                 # кто отвечает за содержимое
enforcement: lint                 # lint | hook | test | review | prose
since: "2026-07-28"
---
```

Поле `enforcement` — главное. Оно заставляет ответить, чем правило подкреплено.
Значение `prose` допустимо только для того, что машина проверить не в состоянии:
причины архитектурных решений, договорённости, границы ответственности.
Всё остальное с `prose` — кандидат на переезд в линтер.

Правила пиши проверяемыми: «отступ 2 пробела» вместо «форматируй правильно»,
«валидация только в FormRequest» вместо «валидируй данные».
Держи файл в пределах 15 пунктов — длинные правила соблюдаются хуже.

### 4. Вынеси автоматизируемое в `configs/`

Готовые конфиги линтеров (`phpstan.neon`, `eslint.config.js`, `ruff.toml`),
которые проект подключает у себя. Каждое правило с `enforcement: lint`
обязано иметь соответствие здесь — иначе это не lint, а prose.

### 5. Добавь модуль в `.claude-plugin/marketplace.json`

Без этой записи модуль не установится.

### 6. Прогони тесты

```bash
tests/run.sh
```

Валидация проверит: структуру, frontmatter, размеры, дубли `paths:` между
модулями и валидность JSON. Красный тест — модуль не готов.

### 7. Заведи фикстуру для проверки загрузки

В `tests/fixtures/` добавь файл-образец, подходящий под `paths:` нового модуля,
чтобы `tests/test-context.sh` мог проверить, что правило реально грузится.

## Когда правило вообще заводить

Только по факту, не впрок:
- модель ошиблась одинаково второй раз;
- код-ревью поймало то, что модель должна была знать;
- одну и ту же поправку печатаешь в чат второй раз подряд.

«Давайте на всякий случай запишем всё, что знаем» — самый быстрый способ
превратить репозиторий в текст, который никто не читает и который раздувает
контекст в каждой сессии.
