# HTTP API: контракт

Контракт API — единственная часть системы, которую ломают чужие клиенты,
а не свои тесты. Поэтому здесь дороже всего стоит непродуманное решение
и дешевле всего — соглашение, принятое один раз.

- **Версионирование обязательно** и вводится сразу, а не когда понадобится
  ломающее изменение. Добавить версию к работающему API дороже, чем
  предусмотреть её заранее.
- Тело запроса и ответа — JSON. Поля в camelCase, единообразно по всему API:
  смесь стилей заставляет клиента помнить исключения.
- Пути методов в kebab-case, существительные для ресурсов, действие
  выражается методом HTTP, а не словом в пути.
- **Имена полей от общего к частному** (`orderStatus`, а не `statusOfOrder`),
  общее выносится в верхние объекты, а не повторяется префиксом в каждом поле.
- Имя поля максимально простое. Сокращения не экономят ничего, кроме символов,
  и стоят вопроса при каждом чтении.
- Коды ответов осмысленные: 4xx — ошибка вызывающего, 5xx — своя. Ответ 200
  с полем `error` внутри заставляет клиента разбирать тело, чтобы понять,
  сработало ли, и ломает любую стандартную обработку.
- Клиент API описывает **все** сущности — и передаваемые, и получаемые.
  Разбор ответа «на месте» по ключам массива означает, что контракта нет.
- Наружу не отдаём сущность хранилища напрямую: добавленное в таблицу поле
  иначе немедленно оказывается в публичном контракте.
- Схема (OpenAPI) собирается из кода автоматически или полуавтоматически.
  Схема, поддерживаемая руками, расходится с реальностью в первый же месяц.
- **Изменение существующего контракта — ломающее изменение.** Тесты проверяют
  свою сторону, а ломается чужая. Нужен человек и, как правило, новая версия.
- Ошибки во всём API имеют одинаковую структуру: код, сообщение, детали.
  Разные форматы ошибок на разных эндпоинтах — это несколько API под одним
  адресом.
