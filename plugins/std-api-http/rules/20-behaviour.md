# HTTP API: поведение под нагрузкой и во времени

Контракт описывает форму данных. Всё остальное — что будет при повторе,
при тысяче записей, при отказе — контрактом обычно не описано, и именно там
живут ошибки, которые находит клиент, а не автор.

- Списки постраничны всегда, с ограничением по умолчанию и максимумом.
  Метод, отдающий всё, работает год, а потом становится причиной отказа.
- Постраничность по курсору для растущих данных: смещение сдвигается при
  вставке, и клиент видит одну запись дважды, а другую не видит вовсе.
- Операции записи, которые клиент может повторить, идемпотентны — по ключу
  идемпотентности или по естественной уникальности. Сеть повторяет запросы
  без спроса.
- Метод изменения возвращает результат, а не пустоту: клиенту нужен новый
  вид сущности, иначе он запросит её отдельно и получит гонку.
- Частота запросов ограничена, ограничение видно в заголовках. Клиент должен
  узнавать о лимите из ответа, а не из отказа.
- Долгие операции выполняются асинхронно: ответ 202 с адресом статуса.
  Запрос, длящийся минуту, обрывается любым посредником.
- Кэширование объявлено заголовками (`ETag`, `Cache-Control`). Без них
  посредники кэшируют по своему усмотрению, включая приватные ответы.
- Фильтры и сортировка описаны явным списком допустимых полей. Свободная
  строка условия — это и инъекция, и невозможность построить индекс.
- Частичное обновление и полная замена различаются (`PATCH` и `PUT`).
  Один метод для обоих смыслов приводит к затиранию полей, о которых клиент
  не знал.
- Формат времени один на всё API — ISO 8601 с зоной. Смесь форматов
  обнаруживается на клиенте в проде.
- Правила доступа к API из браузера заданы явным списком источников,
  а не разрешением для всех.
- Ошибка содержит машиночитаемый код, а не только текст. Клиент, разбирающий
  сообщение строкой, ломается при первой правке текста.
