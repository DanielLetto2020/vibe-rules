# CSS: организация стилей

Стиль пишется один раз, а живёт вместе с проектом. Вопрос не в том, как
оформить правило, а в том, где оно окажется через год и кто рискнёт его
удалить. Неудаляемый CSS — главная причина, по которой файлы стилей только
растут.

- У каждого стиля есть очевидное место: токены, база, компоненты, утилиты.
  Правило, положенное «пока сюда», остаётся там навсегда.
- Стиль компонента живёт рядом с компонентом (`scoped`, CSS-модуль или
  файл того же имени). Глобальный файл — только для токенов и базы.
- Порядок слоёв задаётся явно (`@layer`), а не порядком импортов. Иначе
  перестановка строки в точке входа меняет вид страницы.
- Правило пишется на класс, а не на тег: `h2 { margin-top: 2rem }` в общем
  файле выстрелит там, где про него не думали.
- Именование по одной схеме на проект (BEM, утилиты, что угодно) — важна
  не схема, а её единственность.
- Утилитарные классы не смешиваются с семантическими в одном компоненте
  без причины: `class="card mt-4 p-2 flex"` — это стиль, размазанный между
  разметкой и таблицей стилей.
- Магические числа сопровождаются причиной или заменяются токеном.
  `margin-left: 37px` через полгода нельзя ни изменить, ни удалить.
- Обнуление отступов делается сбросом в базе один раз, а не `margin: 0`
  в каждом компоненте.
- Медиазапросы живут рядом со своим правилом, а не отдельным файлом
  «мобильная версия»: разнесённые, они расходятся при первом же изменении.
- Вложенность (в SCSS или нативная) не глубже трёх уровней: каждая ступень
  повышает специфичность и делает правило неперебиваемым.
- Удаление стиля должно быть безопасным. Если непонятно, кто пользуется
  классом, — это проблема организации, а не смелости.
- Автопрефиксы и поддержка старых браузеров — задача сборки, а не рук:
  дублирующие свойства, вписанные вручную, устаревают молча.
