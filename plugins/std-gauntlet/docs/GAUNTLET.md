# Строй проверок: зачем каждая ступень

Цель конвейера — довести систему до состояния, в котором отказ от чтения кода
перестаёт быть безрассудством. Не «доверять агенту», а сделать так, чтобы
недоверие было автоматизировано.

## Пять ступеней

Каждая следующая проверяет предыдущую. Пропуск любой обесценивает те, что ниже.

### 1. Спецификация — человек

Единственный документ, который читают глазами всегда. Написан человеческим
языком, без артефактов кода. Отвечает на вопрос «что должно происходить».

**Что ловит:** неправильно понятое требование.
**Чего не ловит:** ничего больше. Всё остальное ниже.

Если спека врёт, все проверки ниже честно охраняют неправильное поведение.
Это единственное место, где ошибка не ловится ничем.

### 2. Тесты — из спеки, независимо от реализации

**Что ловит:** несоответствие поведения спецификации.
**Чего не ловит:** свою собственную слабость. Тест, который не может упасть,
проходит всегда.

Ключевое условие — независимость. Когда один и тот же контекст порождает
и код, и проверку к нему, предположения не проверяются, а подтверждаются:
ошибка и её проверка получаются согласованными.

### 3. Мутационное тестирование — проверка тестов

**Что ловит:** слабые тесты. Мутант выжил — значит код можно сломать в этом
месте, и никто не заметит.
**Чего не ловит:** неправильную спецификацию. Тест может убивать всех мутантов
и проверять неправильное требование.

Это единственная ступень, которая проверяет надзорный слой. Без неё покрытие
превращается в самообман: набор со 100% покрытия и 4% убитых мутантов
исполняет каждую строку и пропускает почти все ошибки.

### 3б. Мутация данных спецификации

Второй вид мутации, и он ловит то, чего не ловит первый.

Тест может убивать всех мутантов кода и при этом **не быть связанным
со спецификацией**: он проверяет собственные захардкоженные значения, а не те,
что записаны в сценарии. Такой тест зеленеет при любой правке требования —
то есть охраняет не то, что заказано.

Проверка простая: меняем в сценарии `заказ на 1000 рублей` на `1001`.
Тест остался зелёным — он этих данных не читает.

```bash
gherkin-mutate.py --dry-run                       что будет испорчено
gherkin-mutate.py --run "vendor/bin/behat"        прогон
```

Портятся три вещи: число сдвигается на единицу (ловит границы), число
обнуляется (ловит пустой случай), значение в кавычках подменяется заведомо
другим.

```
Мутация данных: убито 0 из 4 (score 0%)

Выжившие мутанты — тесты не читают эти значения:
  features/discount.feature:4  [число сдвинуто]
    было:  Дано заказ на 1000 рублей
    стало: Дано заказ на 1001 рублей
```

Гейт `spec-mutation` добавляется автоматически, если в проекте есть каталог
со сценариями. Храповик к нему не применяется: выживший мутант данных означает
разрыв между тестом и требованием, и послаблений тут не бывает.

**Что ловит:** тесты, живущие отдельно от спецификации.
**Чего не ловит:** по-прежнему неправильную спецификацию. Связь есть, а верна
ли сама спека — вопрос к ступени 1.

Оговорка: если в сценариях нет конкретных значений («Дано корректный заказ»),
портить нечего — и это само по себе сигнал, что сценарий мало что проверяет.

### 4. Метрики — вместо чтения диффа

Покрытие, цикломатическая сложность, размеры модулей, направление
зависимостей, дублирование.

**Что ловит:** структурную деградацию — разрастание, запутывание, циклы
в зависимостях.
**Чего не ловит:** правильность. Красивые метрики у неправильного кода —
обычное дело.

#### Покрытие изменённых строк

Гейт `diff-coverage` считает долю строк этой работы, которые выполнил хоть
один тест. «Эта работа» — всё, что отличается от общего предка с основной
веткой; на самой основной ветке — рабочее дерево против последнего коммита,
вместе с тем, что уже в индексе, и с новыми файлами.

| Код | Значит |
|---|---|
| `0` | порог взят или изменённых строк кода нет |
| `1` | ниже порога — прогон красный |
| `3` | **не проверено**: нет отчёта, отчёт не про этот проект, неглубокий клон без общего предка, не git — прогон продолжается, в итоге «не проверено» |
| `2` | ошибка запуска самого скрипта — прогон красный |

Файл, которого нет в отчёте, не пропускается. Если рядом с ним инструмент
измерил другие файлы (тот же каталог верхнего уровня или корень `<source>`),
значит этот не выполнил ни один тест — его строки кода засчитываются
непокрытыми. Тесты, объявления типов и конфиги сборки в знаменатель не идут;
каталоги, которые инструмент не измеряет вовсе (миграции, маршруты), названы
в выводе, но не учитываются. Исключить файл — решение человека, записанное
в конфигурации:

```json
{ "diffCoverage": { "min": 80, "report": "coverage.xml", "base": "origin/main",
                    "exclude": ["scripts/*", "src/generated/*"] } }
```

В CI нужна история до общего предка: `actions/checkout` по умолчанию берёт
глубину 1, и тогда гейт честно отвечает «не проверено». Лечится
`fetch-depth: 0`.

### 5. Список для человеческих глаз

**Что ловит:** то, что не ловится ничем выше.

- миграции и схема БД — откат данных невозможен
- изменения API-контракта — ломается чужая сторона
- новые зависимости — пакет проходит все проверки идеально
- деньги, права, персональные данные
- манифесты k8s, playbook'и, конфигурация CI

Этот список не сокращается по мере роста автоматизации. Это нормально.

## Прогон и замок на коммит

```bash
gauntlet.sh                  все гейты; успех ставит отметку для коммита
gauntlet.sh --fast           без мутации — для итераций, отметку не ставит
gauntlet.sh --only lint      один гейт или семейство (js-lint, py-lint)
gauntlet.sh --only mutation  вся мутация кода, как бы гейты ни назывались
gauntlet.sh --list           что будет запущено
```

Прогон не зеленеет там, где проверка не состоялась:

- имя в `--only`, которого нет, и неизвестный аргумент — ошибка с кодом 2,
  а не «все гейты пройдены» по пустому списку;
- `.claude/gauntlet.json` есть, а `jq` нет — код 2: гейты по умолчанию
  вместо настроенных были бы прогоном не тех проверок;
- при храповике порог самого инструмента выключен, поэтому mutation score
  обязан прочитаться — не прочитался, гейт провален. Читается MSI у Infection
  (не «Covered Code MSI»), строка `All files` итоговой таблицы Stryker,
  сводка mutmut из эмодзи. Через храповик идёт любой гейт мутации кода —
  и тот, что назван не по слову `mutation`, но берёт `$MSI`;
- `mutation.enabled: false` пропускает гейты мутации кода, даже если они
  остались в `gates` после смены профиля.

Отметка успешного прогона (`.claude/.gauntlet-pass`) — не время, а отпечаток
содержимого рабочего дерева: id дерева git из всех отслеживаемых и новых
файлов, кроме игнорируемых. Снимается **до** прогона — проверено то, что
лежало на диске в начале. Замок `guard-commit` снимает отпечаток заново
перед коммитом и спрашивает, если он не совпал, называя изменённые файлы.

Что это меняет по сравнению с прежним сравнением mtime исходников семи
расширений: замечаются `.tsx`, `.rs`, `package.json`, сценарии, удаление
теста и переименование через `mv`. `git add` и частичный коммит отпечатка
не меняют — содержимое то же. Правка, сделанная во время долгого прогона,
проверенной не считается: отметка не ставится, прогон надо повторить.
Отчёты и логи, которые записал сам прогон и которых нет в `.gitignore`,
в сверку не входят — прогон называет их, чтобы их туда добавили.
Проваленный прогон снимает прежнюю отметку.

Коммитом замок считает и `git -C … commit`, `git -c k=v commit`,
`git --no-pager commit`, `/usr/bin/git commit`, `bash -c "git commit"`,
и команды, создающие коммит без этого слова: `merge`, `cherry-pick`,
`revert`, `am`, `pull`.

## Порядок внедрения

Не выстраивать все пять сразу — утонешь и бросишь.

**Шаг 1. Измерить.** Поставить мутационное тестирование на один некритичный
сервис и посмотреть фактический mutation score при текущем покрытии. Цифра
обычно неприятная — она и есть аргумент за всё остальное.

**Шаг 2. Заборы.** Довести score до порога, сделать порог блокирующим в CI.
С этого момента появился первый настоящий забор.

**Шаг 3. Процесс.** Спеки до кода, разделение сессий, характеризационные тесты
для легаси.

**Шаг 4. Только теперь** осторожно уменьшать долю кода, который читается
глазами, — и смотреть месяц, сколько система ловит без человека.

Первые недели это дороже, а не дешевле: забор надо построить, мутационные
прогоны стоят времени и денег. Экономия начинается позже.

## Чего конвейер не даёт

Честные границы важнее полноты:

- производительность, гонки, стоимость эксплуатации — тесты на счастливом
  пути их не видят;
- архитектурная энтропия — код может быть корректным и нерасширяемым;
- правильность самой спецификации;
- вредоносная зависимость.

Отдельно: конвейер рассчитан на систему с наблюдаемой границей. Для легаси
без спецификации сначала применяется характеризация (скилл
`legacy-characterize`), и только потом обычный конвейер.
