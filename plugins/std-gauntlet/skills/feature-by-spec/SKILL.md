# Новая функциональность по конвейеру

Порядок здесь не косметический. Тест, написанный после реализации, проверяет
то, что получилось, а не то, что требовалось, и как надзорный слой бесполезен.

## 1. Спека — до всего остального

Сформулируй поведение на человеческом языке и **покажи пользователю до начала
работы**. Формат Gherkin, без артефактов уровня кода:

```gherkin
Функция: Оплата заказа

  Сценарий: успешная оплата
    Дано заказ на 1500 рублей в статусе "ожидает оплаты"
    Когда покупатель оплачивает его картой
    Тогда заказ переходит в статус "оплачен"
    И покупателю уходит письмо с чеком

  Сценарий: повторная оплата не проходит
    Дано заказ в статусе "оплачен"
    Когда покупатель оплачивает его ещё раз
    Тогда деньги не списываются
    И покупатель видит сообщение "заказ уже оплачен"
```

Обязательно перечисли несчастливые пути: нет прав, невалидный ввод, повтор
операции, внешний сервис недоступен, конкурентное изменение.

Значения в примерах — конкретные. Они потом мутируются, чтобы проверить, что
тест вообще связан с приложением.

**Не начинай кодировать, пока пользователь не подтвердил спеку.** Это
единственная точка, где ошибка не ловится ничем ниже по конвейеру.

## 2. Тесты — из спеки, до реализации

Переведи каждый сценарий в тест. Запусти и **убедись, что тесты падают**,
причём по правильной причине: «метод не найден» — правильно, «синтаксическая
ошибка в тесте» — нет.

Тест обращается к приложению через его публичную границу (HTTP-эндпоинт,
консольная команда, публичный сервис), а не к внутренностям. Тогда рефакторинг
не будет ломать тесты.

Если в проекте принято разделение сессий — на этом шаге остановись и скажи
пользователю, что тесты готовы и реализацию делает отдельная сессия.

## 3. Реализация

Минимальный код, доводящий тесты до зелёного. Не «на будущее», не «раз уж
я здесь». Всё лишнее — это непроверенный код, попавший в систему под видом
проверенного.

Соблюдай правила слоёв того стека, с которым работаешь: они уже загружены
по путям файлов.

## 4. Прогон гейтов — всех, не выборочно

```
/std-gauntlet:run
```

Красный гейт означает, что работа не сделана. Не «почти готово», не «падает
только один тест».

## 5. Мутационное упрочнение

Если mutation score ниже порога — выжившие мутанты показывают конкретные места,
где тесты ничего не охраняют. Не поднимай порог и не удаляй мутантов из отчёта:
добавь ассерты, которых не хватает.

Разбор выживших: скилл `mutation-harden`.

## 6. Отчёт с разделом для человека

В конце отдельно перечисли изменения, требующие человеческих глаз:

- миграции и изменения схемы БД
- изменения существующего API-контракта
- новые зависимости
- всё, связанное с деньгами, правами доступа и персональными данными
- манифесты k8s, playbook'и, конфигурация CI

Если ничего из этого нет — скажи об этом прямо. Пустой список — тоже
информация: он означает, что изменения можно принимать по зелёным гейтам.
