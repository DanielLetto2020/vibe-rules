# SQLite в тестах

SQLite берут для тестов ради скорости, и это разумно. Опасность в другом:
зелёный набор тестов на SQLite создаёт уверенность в коде, который на боевой
СУБД ведёт себя иначе. Ложная уверенность хуже отсутствия тестов.

- Тесты, проверяющие работу с базой всерьёз, идут на той же СУБД, что
  в проде. На SQLite остаётся быстрый поднабор для логики, не зависящей
  от диалекта.
- Всё, что связано с типами возвращаемых значений, сортировкой,
  регистрозависимостью и параллельным доступом, на SQLite не проверяется:
  результат не переносится.
- Проверка целостности включается явно на каждом соединении, иначе тесты
  пропускают нарушения внешних ключей, которые прод поймает.
- Схема для тестов создаётся теми же миграциями, что и рабочая. Отдельный
  файл схемы для тестов расходится с реальной и делает набор бесполезным
  ровно тогда, когда он нужнее всего.
- Особенности диалекта (частичные индексы, оконные функции, типы) в тестах
  не обходятся заглушками: обход означает, что тестируется не тот код,
  который поедет в прод.
- База в памяти живёт в пределах соединения. Пул соединений в тестах даёт
  «таблица не найдена» на втором запросе, и это не ошибка кода.
- Каждый тест начинает с известного состояния: транзакция с откатом
  или пересоздание базы. Общая база между тестами связывает их порядком.
- Данные для тестов создаются фабриками с явными значениями там, где они
  проверяются. Общий набор записей, от которого зависят двадцать тестов,
  ломает их все при первом изменении.
- Файл тестовой базы не коммитится и лежит во временном каталоге.
- Если проект на SQLite и в проде — тесты идут на нём же, и все правила
  выше про расхождение диалектов не действуют. Различать эти два случая
  обязательно: они требуют противоположного.
