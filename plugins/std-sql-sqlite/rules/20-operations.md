# SQLite: эксплуатация

SQLite — это файл, а не сервис. Всё, что в обычной СУБД делает администратор,
здесь делает приложение: настраивает соединение, следит за размером, снимает
копии. Не делает — значит, этого не происходит.

- Настройки задаются на каждом соединении, а не один раз при создании базы:
  `foreign_keys`, `journal_mode`, `busy_timeout`. Пул открывает новые
  соединения, и настройки по умолчанию возвращаются.
- `busy_timeout` задан явно. Без него параллельная запись немедленно получает
  ошибку блокировки вместо ожидания.
- Копия снимается штатным механизмом резервного копирования, а не копированием
  файла на ходу: рядом с базой лежит журнал, и копия без него бесполезна.
- Файл базы лежит вне каталога, раздаваемого веб-сервером, и вне образа
  контейнера: в образе он теряется при перевыкладке.
- Размер контролируется. Удаление строк не уменьшает файл; место возвращает
  только явная упаковка, и она блокирует базу на время работы.
- Транзакция на пачку записей вместо записи по одной: каждая отдельная
  вставка — это сброс на диск.
- Записи выполняются одним процессом. Если писателей несколько, нужна
  очередь на уровне приложения или другая СУБД.
- Тип колонки объявляется, даже если движок его не соблюдает: он остаётся
  документацией и понадобится при переезде.
- Дата хранится в одном формате — текст ISO или число. Смесь делает
  сортировку и сравнение бессмысленными.
- Полнотекстовый поиск — через встроенный модуль, а не через `LIKE '%…%'`:
  последний читает таблицу целиком.
- Переезд на другую СУБД планируется заранее, если проект растёт. Признаки:
  второй экземпляр приложения, объём в гигабайтах, потребность в правах
  доступа.
