# Python-парсеры: разбор, нормализация, хранение

Источник меняется без предупреждения, и главный вопрос к парсеру не «умеет ли
он разобрать страницу», а «поймём ли мы, что он перестал». Молчаливая деградация
здесь опаснее падения.

- Селекторы и правила разбора собраны в одном месте, а не разбросаны по коду.
  Смена вёрстки источника должна чиниться в одном файле.
- Пустой результат — это ошибка, а не пустой список. Парсер, вернувший ноль
  записей вместо тысячи, обязан сообщить об этом, а не записать пустоту.
- Ожидаемый объём проверяется: резкое изменение числа записей или доли пустых
  полей означает, что источник изменился.
- Нормализация выполняется на входе и по одним правилам: пробелы, регистр,
  телефоны, даты, числа с разными разделителями. Дальше в системе живут
  только нормализованные значения.
- Даты приводятся к одной зоне с сохранением исходной строки: «12.07.2026»
  без зоны и без источника невозможно перепроверить.
- Числа с разделителями разбираются явно. `float("1,234")` даёт разное
  в разных локалях и вообще падает — правила разбора задаются, а не наследуются
  от системы.
- У каждой записи есть устойчивый ключ из данных источника. Индекс в списке
  или порядковый номер строки ключом быть не может.
- Повторный запуск не создаёт дубликаты: вставка по ключу с обновлением.
  Парсер запускают повторно всегда — после сбоя, после правки, после переезда.
- Сырой ответ сохраняется отдельно от разобранных данных. Изменение правил
  разбора должно применяться к уже собранному без повторного обхода источника.
- Инкрементальность опирается на признак изменения из источника, а не на
  «время последнего запуска»: пропущенный запуск иначе означает пропущенные
  данные навсегда.
- Частичный отказ не отменяет всю работу: запись, которую не удалось
  разобрать, откладывается с причиной, остальные сохраняются.
- Персональные данные из источника не складываются «на всякий случай» —
  собирается только то, что нужно для задачи.
