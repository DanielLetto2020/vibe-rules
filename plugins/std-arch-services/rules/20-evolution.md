# Сервисы: изменение и согласованность

Пока сервис один, изменение — это выкладка. Как только их два, изменение —
это переговоры: у соседа своя очередь релизов, свои клиенты и своя копия
представления о ваших данных.

- Изменение контракта совместимо по умолчанию: добавляем необязательное,
  не удаляем и не меняем смысл существующего. Несовместимое изменение —
  это новая версия и период, когда работают обе.
- Старая версия выключается по факту, а не по плану: сначала смотрим, кто
  ещё её вызывает, потом отключаем. Без учёта вызовов отключение —
  это авария у неизвестного заранее сервиса.
- Выкладка сервисов независима. Требование «сначала выложить А, потом Б»
  означает, что это один сервис, разрезанный на два.
- Данные принадлежат одному сервису. Копия у соседа допустима как кэш
  с явным сроком и признаком устаревания, а не как второй источник истины.
- Операция, затрагивающая два сервиса, не оборачивается в общую транзакцию —
  её нет. Либо последовательность шагов с компенсацией, либо пересмотр
  границы: возможно, разрез прошёл не там.
- Согласованность отложенная, и это видно в интерфейсе: «заявка принята»
  вместо «выполнено», если результат придёт позже.
- Каждый вызов соседа имеет таймаут, ограниченное число повторов
  и поведение при отказе. Повтор без ограничения превращает замедление
  соседа в отказ всей цепочки.
- Отказ соседа деградирует функцию, а не сервис целиком: недоступность
  рекомендаций не должна мешать оформить заказ.
- Общий код между сервисами — только для контракта и клиента. Общая
  библиотека с бизнес-логикой связывает выкладки обратно в одну.
- Новый сервис заводится, когда есть причина: отдельная нагрузка, отдельный
  цикл выпуска, отдельная команда, отдельные требования к доступности.
  «Так современнее» причиной не является.
