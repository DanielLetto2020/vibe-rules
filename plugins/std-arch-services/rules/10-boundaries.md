# Границы между сервисами

Граница, которую можно обойти, не является границей. Прямое обращение
к чужому хранилищу выглядит как экономия одного запроса, а обходится
невозможностью изменить схему без согласования со всеми, кто в неё заглядывает.

- **Сервис не обращается к базе, кэшу или очереди другого сервиса напрямую** —
  только через его HTTP API. Чужая схема БД не является контрактом
  и меняется без предупреждения.
- Признак нарушения, который видно в конфигурации: в переменных окружения
  сервиса указаны реквизиты хранилища, принадлежащего другому сервису.
- Синхронное взаимодействие — HTTP API с авторизацией каждого запроса
  подписанным токеном. Доверие по сетевому адресу или внутренней подсети —
  не авторизация.
- Асинхронное — через брокера, с авторизацией и **описанной схемой
  сообщения**. Сообщение без схемы становится неизменяемым: никто не знает,
  кто его читает и что сломается от нового поля.
- Общая точка авторизации для внутренних пользователей: сервис проверяет
  токен, но не заводит собственных паролей. Каждое отдельное хранилище
  учётных данных — отдельный инцидент в будущем.
- Отказ соседнего сервиса — ожидаемое состояние, а не исключение: таймаут,
  ограниченные повторы, понятная деградация. Сервис, падающий вместе
  с соседом, не отдельный сервис.

## Шлюз

- Шлюз содержит только маршрутизацию, ограничение частоты запросов
  и фильтрацию структуры запроса и ответа.
- **Бизнес-логики в шлюзе нет.** Логика, оказавшаяся там, не покрыта тестами
  сервиса, не видна в его коде и обнаруживается только при разборе инцидента.
- Шлюз не единственный слой авторизации: сервис проверяет токен сам, иначе
  прямое обращение в обход шлюза открывает всё.
