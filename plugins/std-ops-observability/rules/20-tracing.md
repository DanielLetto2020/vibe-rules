# Наблюдаемость: показатели, трассировка, дежурство

Мониторинг заводят, чтобы узнавать о поломках раньше пользователей. Проверить
это можно единственным способом: посмотреть, откуда узнали о последних трёх
инцидентах. Если из жалоб — мониторинга нет, есть графики.

- Показатели отвечают на вопрос «работает ли сервис для пользователя»:
  доля ошибок, время ответа по перцентилям, объём запросов. Среднее время
  ответа скрывает именно тех, кому плохо.
- Метка метрики не содержит значений с неограниченным множеством:
  идентификатор пользователя, URL с параметрами, текст ошибки. Каждое новое
  значение — отдельный ряд, и хранилище кончается за сутки.
- Целевой уровень обслуживания назван числом до того, как случился инцидент.
  Без него спор «это уже деградация или ещё нет» решается громкостью.
- Оповещение приходит на симптом, а не на причину: «доля ошибок выросла»
  вместо «загрузка процессора 90%». Второе бывает нормой, первое — никогда.
- Каждое оповещение указывает, что делать. Сигнал без инструкции
  через полгода игнорируют.
- Оповещения, на которые никто не реагирует, удаляются. Канал, где половина
  сообщений — шум, работает как выключенный.
- Трассировка сквозная: идентификатор запроса создаётся на входе и передаётся
  во все вызовы, включая очереди и фоновые задачи. Разрыв цепочки на границе
  очереди — самое частое место, где след теряется.
- Записываются длительность и результат внешних вызовов. Замедление чужого
  API иначе выглядит как замедление своего кода.
- Панель наблюдения начинается с состояния сервиса, а не с графиков
  инфраструктуры: во время инцидента первым нужен ответ «что видит
  пользователь».
- Выкладки отмечаются на графиках. Половина инцидентов начинается
  с выкладки, и это первое, что стоит проверить.
- Инцидент завершается разбором с записанной причиной и действием. Разбор,
  не породивший изменения, — это пересказ.
