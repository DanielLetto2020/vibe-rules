# Архитектурные решения

Архитектура — это набор решений, которые дорого менять. Дорого не потому, что
кода много, а потому, что причина решения забылась: никто не знает, можно ли
трогать, и на всякий случай не трогает.

- Решение записывается там же, где живёт код, и содержит три вещи: что
  выбрали, из чего выбирали, почему. Без отвергнутых вариантов запись
  бесполезна — через год ровно их и предложат снова.
- Записываются только решения, которые дорого отменить: хранилище, способ
  взаимодействия между сервисами, модель данных, граница модуля. Выбор
  библиотеки для дат таким не является.
- У решения есть дата и состояние. Отменённое решение не удаляется,
  а помечается вместе с тем, что пришло взамен: история важнее аккуратности.
- Решение принимается под текущий объём и известное будущее. «Заложим
  на вырост» без названного срока и числа — это плата сложностью за событие,
  которое может не наступить.
- Модуль выделяется по причине изменения, а не по типу файлов. Каталоги
  `controllers`, `services`, `models` группируют одинаковое; правка одной
  функции при этом задевает три каталога.
- Граница проверяется вопросом: можно ли изменить внутренности, не трогая
  вызывающий код. Если нельзя — это не модуль, а каталог.
- Зависимости между модулями направлены в одну сторону и не образуют циклов.
  Цикл означает, что модули на самом деле один.
- Общий код выносится, когда одинаковое поведение повторилось третий раз.
  Раньше — обобщение по совпадению, а оно расходится при первом же различии.
- Обобщение отменяется, если разошлось: две похожие функции честнее одной
  с флагом, меняющим её поведение.
- Смена архитектурного подхода — отдельная задача с планом и границей.
  Половина проекта в новом стиле и половина в старом хуже, чем весь проект
  в старом.
