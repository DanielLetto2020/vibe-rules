# Python: пакеты, зависимости, окружение

В Python легко получить работающий у себя код, который не запускается больше
нигде: интерпретатор находит модули по путям, которые у каждого свои,
а зависимости ставятся глобально и молча конфликтуют.

- Зависимости объявлены в `pyproject.toml`, версии зафиксированы файлом
  блокировки, файл коммитится. «У меня работает» почти всегда означает
  другой набор версий.
- Виртуальное окружение обязательно, установка в системный интерпретатор
  запрещена: она ломает и проект, и систему.
- Импорты абсолютные. Относительные с точками (`from ..utils import x`)
  ломаются при переносе модуля и мешают запускать файл напрямую.
- Циклические импорты не обходятся импортом внутри функции — это отложенная
  та же ошибка. Циклом ведает структура, а не место импорта.
- Пакет не выполняет работу при импорте: `__init__.py` содержит объявления,
  а не подключения к базе и не чтение файлов.
- Точка входа отделена от логики: `if __name__ == "__main__"` вызывает
  функцию, а не содержит скрипт. Иначе модуль нельзя ни импортировать,
  ни протестировать.
- Настройки читаются в одном месте, валидируются при старте и типизированы.
  `os.environ["X"]` посреди кода — отказ в рантайме на проде.
- Модуль знает своё назначение: `utils.py`, куда складывают всё подряд,
  через год связывает половину проекта со второй половиной.
- Данные и код разделены: пути к файлам данных берутся из настроек или
  ресурсов пакета, а не собираются от `__file__` вручную.
- Логирование через `logging` с именем модуля, а не `print`. `print`
  невозможно ни отключить, ни перенаправить, ни разметить уровнем.
- Версия Python зафиксирована и совпадает с той, что стоит в контейнере
  и в CI. Расхождение проявляется на синтаксисе, которого нет в младшей.
