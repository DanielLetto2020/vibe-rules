# Redis: приёмы и подводные камни

Кэш добавляют, когда медленно, и обычно это помогает — до первого всплеска
или первого перезапуска. Ошибки кэширования проявляются ровно в тот момент,
когда система под нагрузкой, то есть когда цена ошибки максимальна.

- Одновременный промах по популярному ключу отправляет всю нагрузку
  в источник разом. Пересчёт защищается блокировкой или продлением старого
  значения на время обновления.
- Срок жизни ключей одной группы разбавляется случайной добавкой: иначе
  всё, прогретое одним запросом, истечёт одновременно.
- Кэш не используется как единственное хранилище. Redis может потерять
  данные при перезапуске, и любая запись, существующая только там, —
  потеря, а не задержка.
- Отсутствие результата тоже кэшируется, с коротким сроком: иначе запросы
  за несуществующей записью каждый раз доходят до базы.
- Значения хранятся небольшими. Ключ на мегабайты блокирует сервер на время
  передачи и вытесняет из памяти всё остальное.
- Структура данных выбирается по задаче: список, множество, хеш,
  упорядоченное множество. Хранение JSON-строки там, где нужно поле,
  заставляет читать и писать целиком.
- Команды, обходящие всё пространство ключей, в рабочем коде запрещены;
  для перебора — курсорный обход пачками.
- Операции над несколькими ключами выполняются одной пачкой или сценарием
  на стороне сервера: последовательность из ста обращений — это сто
  сетевых задержек.
- Политика вытеснения при заполнении памяти задана осознанно. По умолчанию
  сервер начинает отказывать в записи вместо освобождения места.
- В кластере ключи одной операции должны попадать на один узел — иначе
  групповая команда невозможна.
- Данные пользователя и общий кэш разделены по пространству имён. Очистка
  «всего кэша» не должна выносить сессии.
- Кэш прогревается после выкладки, если холодный старт заметен: первые
  минуты после перезапуска — самый частый момент отказа под нагрузкой.
