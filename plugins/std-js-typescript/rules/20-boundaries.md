# TypeScript: границы и моделирование

Внутри программы типы работают. Проблемы начинаются там, где данные пересекают
границу: приходят по сети, ложатся в хранилище, уезжают в другой процесс.
На границе тип — это договорённость, которую надо проверять, а не полагаться.

- Тип ответа API и тип доменной модели — разные типы. Когда они один, любое
  изменение на бэкенде расходится по всему коду, а поле, переименованное
  в ответе, приходится переименовывать и в бизнес-логике.
- Преобразование внешнего представления во внутреннее делается в одном месте
  на границе, а не по месту использования. Иначе `snake_case` из API
  просачивается в компоненты.
- Идентификаторы разных сущностей различаются типом (branded type),
  а не только именем переменной. `getUser(orderId)` компилируется, если оба
  просто `string`.
- Дата в передаче — строка ISO с зоной, дата в программе — объект. Смешение
  даёт `"2026-07-29" + 1` и вычисления по строкам.
- Деньги не хранятся числом с плавающей точкой ни в одном типе домена.
  Тип должен делать ошибку невозможной, а не рассчитывать на внимательность.
- Необязательность в типе означает «может отсутствовать по бизнес-смыслу»,
  а не «пока не реализовано». Второе — временное состояние кода, которое
  через год выглядит как первое.
- Объединения по строковому полю (`kind`, `type`, `status`) обрабатываются
  исчерпывающе, с проверкой на `never` в ветке по умолчанию: тогда добавление
  нового варианта ломает сборку, а не поведение в проде.
- Обобщённые типы вводятся, когда есть хотя бы два реальных применения.
  Дженерик «на будущее» усложняет сигнатуру ради случая, который не наступит.
- Тип, описывающий структуру таблицы или ответа, генерируется из источника,
  если это возможно. Руками написанный дубль схемы расходится с ней молча.
- Утилитарные типы (`Pick`, `Omit`, `Partial`) применяются к доменной модели,
  а не копируют её поля заново: копия не обновится вместе с оригиналом.
